Future work for Claude/rangesolver
===================================

- Partition helper via a --enumerate-depth=N mode on rangesolver
  itself (not a separate script): most N-digit strings aren't valid
  prefixes (piece counts run out, or a tile doesn't fit there), so the
  only correct way to find the valid ones is to replay the actual
  search - Grid + PieceSet + get_first_free_loc - down to depth N and
  record every node reached there, instead of continuing to depth 45.
  That's just full_solver truncated at a fixed depth, so it belongs in
  rangesolver.cpp itself rather than a second implementation of the
  placement logic that could drift out of sync.
  Output: one line per valid depth-N prefix. No need to pair adjacent
  prefixes into ranges - since --start/--end already treat a shorter
  string as an entire inclusive subtree (verified with the earlier
  single-prefix tests), each individual depth-N prefix used as both
  --start=P and --end=P is already one complete, disjoint unit of
  work. Pick N so the prefix count comfortably exceeds the number of
  workers/cores available.
  This is also a prerequisite for the client/server system noted
  below, not just a standalone tool: the server needs exactly this
  enumeration to seed its initial "unsearched" pool, so building it
  now is directly reusable later rather than throwaway work.

- Parallel launcher: a wrapper (shell or python) that takes the
  partition list above and runs one rangesolver process per range
  (e.g. one per core), each logging to its own Solutions/soln_log_*.txt
  to avoid write contention, then merges the logs.
  Treat this as a stopgap, not worth over-building: the client/server
  system below replaces this whole manual-orchestration/merge workflow
  with dynamic assignment and centralized storage, and also handles a
  worker stalling or crashing mid-range, which a static "partition and
  launch once" script has no story for at all.

- Resume-from-checkpoint convenience: a flag to read a previously
  printed "path=" progress line directly (instead of retyping it as
  --start) and continue from there to the end of the full search.

- Smarter cell-selection heuristic ("minimum span" / MRV-style): instead
  of always scanning left-to-right, top-to-bottom for the first empty
  cell, scan empty cells that are upper-left corners of empty space and
  measure the empty span to the right and downward from each; pick the
  cell with the smallest such span (right or down) to branch on next.
  Idea is that highly constrained cells (narrow gaps) are more likely
  to reveal dead-end configurations quickly, pruning bad branches
  sooner instead of discovering them much deeper in the search.
  Caveat: this changes the traversal order, so the resulting piece
  sequence would no longer match the current raster-scan-order "hash"
  that rangesolver's --start/--end and solution.py's get_hash() rely
  on. Would need either a new hash/ordering scheme for this variant,
  or to keep it as a separate solver that isn't range-bounded.

- Arbitrary partial-solution seeding: a second way to specify a
  starting point, alongside the --start/--end digit-prefix hash,
  as an explicit list of (x, y, size) tile placements rather than a
  raster-order prefix. Take it either inline on the command line
  (e.g. --seed="x,y,sz;x,y,sz;...") or from a text file (one
  "x y size" placement per line), pre-place those tiles on the grid,
  deduct them from the piece counts, and then run the normal
  backtracking search over whatever remains.
  Motivation: this doesn't require the seed tiles to follow the
  raster-scan placement order at all, so it could back an interactive
  tool where a user sketches a starting layout by dragging tiles into
  the frame (in any order, anywhere), exports the resulting tuple
  list, and hands it to the solver to complete.
  Implementation notes:
  - Validate the seed: sizes within 1-9, in bounds, no overlaps, and
    no size used more times than the puzzle provides (at most `sz`
    tiles of size `sz`).
  - get_first_free_loc's resume-from-hint optimization assumes pieces
    are always placed at or after the previous raster position, which
    an arbitrary seed can violate (it can leave gaps before the "next"
    free cell). After seeding, the first free-cell search needs to
    fall back to scanning from (0,0) once; the hint-based resume
    optimization is safe again for every step after that.
  - The 45-digit hash format doesn't naturally describe an
    out-of-raster-order seed; if a hash is still wanted for the
    resulting solutions, derive it the way solution.py does (sort
    placed corners by raster position after the fact) rather than
    from insertion order.

- Configurable progress print delay: add a --print-delay=SECONDS (or
  similar) flag so PRINT_DELAY doesn't have to be a hardcoded 3.0s
  constant. Useful for quieter long/background runs (larger delay) or
  tighter monitoring while tuning a small range (smaller delay).

- Store found solutions in a lightweight database instead of (or in
  addition to) the ASCII soln_log_*.txt files, to make deduplication
  and querying easy across many runs. Use SQLite, not MySQL: MySQL is
  a client-server database (needs a running daemon, user accounts, a
  network protocol) which is the opposite of lightweight, whereas
  SQLite is a single file, needs no server, and is trivial to query
  from the command line, Python, or C/C++. A "solutions" table with
  the hash as a UNIQUE TEXT column gets deduplication for free via
  INSERT OR IGNORE.
  Likely design: keep rangesolver writing the ASCII logs as it does
  today (simple, safe for many parallel processes writing to separate
  files, no new dependency in the C++ solver), and add a small Python
  ingestion script under tools/ that reuses solution.py's hashing to
  scan one or more soln_log_*.txt files and upsert their hashes into a
  shared solutions.db. Keeps rangesolver.cpp dependency-free while
  giving a single place to dedupe/count/query results from all runs.
  If solution metadata beyond the hash is ever wanted (e.g. which
  --start/--end range or worker found it, when), add columns for that
  at the same time rather than needing a schema migration later.

- [HIGH PRIORITY] Progress rate / ETA estimation: observe how fast solutions are being
  found and predict how long it will take to finish the current run.
  Bumped to high priority after a manual back-of-envelope estimate
  (1564 solutions / 6000s, extrapolated to 1.7M) got the unit
  conversion wrong by ~10x (11 weeks, not 1 week) - a tool that does
  this arithmetic automatically would have caught that immediately.
  Two complementary estimators, since they have different strengths:

  A) Tree-fraction estimator (model-free, works for any --start/--end
     range, full or partial): at each depth, we know which branch
     (tile size) we're currently exploring out of how many were tried
     at that node (i.e. how many sizes were legal/available there).
     Accumulate a running "fraction of this node's siblings completed
     so far" the way Knuth's classic backtracking-tree-size estimator
     does, refining as we go deeper. This gives a continuously
     improving estimate of what fraction of the *current* search range
     has been completed, independent of any assumption about the total
     solution count, so it works even for an arbitrary prefix range.
     ETA = elapsed_time / fraction_done * (1 - fraction_done).

  B) Target-count extrapolation (only valid for a full, unrestricted
     run): use solutions_found_so_far / elapsed_time as a rate, and
     divide the remaining count (target_total - solutions_found) by
     that rate. notes.txt cites Matt Parker's figure of 1,730,280 total
     solutions (352,072 "L" + 1,303,584 "I" + 74,624 other) as a rough
     target for this. Caveat: notes.txt also records that our own
     nsolver run on the n=8 sub-case didn't match Parker's claimed L
     solution counts, so treat 1,730,280 as an unverified rough
     finish line, not a confirmed authoritative total, until that
     discrepancy is understood - surface it as an estimate with a
     visible "unverified target" caveat rather than a hard countdown.

  The two could be shown side by side in the periodic status line
  once solutions_found is nonzero, or (A) alone when running a
  partial range where (B) doesn't apply.

- Merge/dedupe tool (Python, likely tools/merge_solutions.py): take a
  list of input filenames, accepting glob-style wildcards (e.g.
  "Solutions/soln_log_*.txt"; expand them internally with glob() as
  well as accepting whatever the shell already expanded, so a single
  quoted pattern works even for more files than ARG_MAX would allow),
  read every solution block out of each file (same 45-consecutive-
  45-char-lines scan as splitlog.py), and hash each with solution.py's
  get_hash(). Dedupe by hash (first occurrence wins; a hash collision
  between two visually different grids would indicate a bug - worth
  a sanity check/warning if the raw text differs for the same hash).
  Write the unique solutions to a single output file, in decreasing
  hash order - since digit 9 sorts after digit 1 as a plain string/
  numeric comparison, sorting hashes descending reproduces the order
  solutions are naturally discovered by the solvers (largest remaining
  tile tried first at each position), so the merged file reads the
  same way a single from-scratch run's log would.
  Implementation note: for the eventual full corpus (~1.7 million
  solutions across many parallel workers' output files), holding
  every full 45-line ASCII block in memory at once could be a few GB;
  if that matters, only keep (hash, source file, byte offset) triples
  in memory, sort those by hash, and stream each block from disk to
  the output file in that order rather than holding all the text.

- Live graphical viewer (Python, likely tools/live_view.py), to
  replace watching `tail -f` on a solution log in a console: a PyGame
  window that periodically checks a soln_log*.txt file for new data,
  parses the latest complete solution block, and draws it to the
  window - basically solution.py's save_to_png() rendering (same
  colors/PieceLocation logic), but blitting to a pygame.Surface
  instead of writing a PNG to disk each time.
  Needs pygame added as a new tools/ dependency (not currently listed
  in pyproject.toml; solution.py's PNG export only needs Pillow).
  Implementation notes:
  - Poll by checking the file's size/mtime (e.g. every 0.5-1s) before
    re-reading, rather than busy-reading the whole file every frame;
    for a log that eventually holds ~1.7 million solutions, track the
    last-read byte offset and only scan newly appended bytes for
    complete blocks (same 45-consecutive-45-char-line scan as
    splitlog.py) rather than rescanning from the top of the file.
  - Only treat a block as complete once its trailing "---" delimiter
    has also been fully written, to avoid a race where 45 lines look
    complete but the writer is still mid-flush.
  - If multiple new solutions have appeared since the last poll
    (solving faster than the display refresh), default to showing
    only the latest one rather than queuing a backlog; could offer a
    flag later to instead step through every new one in sequence for
    a "demo reel" viewing mode.
  - Keep the pygame event loop responsive (handle window close/resize)
    between polls rather than blocking on file I/O.

- Client/server distributed search (bigger feature). A server hands
  out --start/--end ranges to worker clients on the LAN; clients
  search their assigned range with rangesolver's algorithm and report
  solutions and progress back; the server tracks what's unsearched,
  what's assigned-but-unconfirmed, and what's done.

  Server responsibilities:
  - Maintain three buckets of range state: unsearched, assigned
    (with a deadline), and completed. The initial unsearched set comes
    from the partition helper noted above (a list of --start/--end
    pairs that tile the whole search space).
  - On a client request, pop a range from unsearched, move it to
    assigned with a timeout, and hand it out.
  - Accept periodic progress reports from clients working an assigned
    range (their current "path=" position within the range, plus any
    solutions found since the last report) and persist solutions as
    they arrive - natural fit for the SQLite-backed storage noted
    above, with the server as the single writer instead of needing a
    separate merge step.
  - On a completion report, move the range to completed. On a timeout
    with no completion, don't just requeue the whole original range:
    use the client's last reported path as a new lower bound, and
    requeue only [last_reported_path, original_end] as unsearched -
    this is the "reduce outstanding work" part, avoiding redoing
    ground the client already covered. A range that times out with no
    progress reports at all just goes back to unsearched unchanged.
  - Should be able to report aggregate stats (unsearched / assigned /
    completed range counts, solutions found, combined rate across all
    clients) - ties into the progress-rate/ETA estimation idea above,
    and is a much better place to compute it than any single client.

  Client responsibilities:
  - Discovery: broadcast a small UDP packet (with a recognizable
    magic string, so random LAN broadcast noise doesn't trigger a
    false match) to the LAN broadcast address on a well-known port;
    the server listens there and replies unicast with its TCP
    host:port. Handle the no-response case (retry a few times, then
    give up with an error) and the unlikely multiple-servers-replied
    case. Also support a --server=IP[:PORT] flag to skip discovery
    and connect directly, for cases where broadcast doesn't reach
    (different subnet, broadcast disabled, etc).
  - Everything after discovery (requesting a range, reporting progress
    and solutions, reporting completion) goes over a plain TCP
    connection - UDP is only for the discovery step.
  - Run the assigned range using the existing solver logic (either by
    invoking rangesolver as a subprocess and parsing its output, or by
    linking the search directly into the client) and send progress
    reports at some interval (reusing the same path/depth/solutions
    info rangesolver already prints), batching any newly-found
    solutions in with each report rather than opening a new message
    per solution.

  Protocol notes (to pin down during implementation, not now):
  - A simple line- or length-delimited JSON message format over TCP
    is almost certainly enough given how small and infrequent these
    messages are - no need for a binary protocol.
  - Decide whether the client is a thin wrapper around a rangesolver
    subprocess or a single binary with the network layer built in;
    the subprocess approach keeps the network/orchestration code
    (probably Python, like the rest of tools/) decoupled from the
    performance-critical C++ search.

- Browser-based client, as an alternative front end to the
  client/server system above. The server machine would need to also
  run a small web server; browser clients on the LAN would load a
  page from it and connect for live updates. Candidates: a small
  vanilla JS page drawing to a <canvas> (simplest - no build step,
  trivially served as a static file, lightweight for a fast-moving
  hobby project), or a Godot project exported to web (a real 2D
  engine, nicer if the visualization grows more elaborate/animated,
  at the cost of a build/export pipeline). Lean toward vanilla JS
  first unless the visuals want to get considerably richer.

  Discovery/protocol differences from the native client noted above:
  - Browsers can't send raw UDP broadcasts or open arbitrary TCP
    sockets, so the earlier discovery mechanism doesn't carry over as
    is. Simplest path: the user just navigates to the server's
    address directly (bookmark or mDNS/Bonjour name like
    partridge.local instead of a raw IP, so they don't have to look
    up the IP each time). Real-time updates then go over WebSocket
    rather than a plain TCP socket.
  - Worth considering unifying on WebSocket+JSON as the one protocol
    for both native and browser clients (a native client can speak
    WebSocket too), rather than maintaining a separate TCP wire
    format for native and a WebSocket one for the browser.

  Display: reuse the same tile color scheme as solution.py's
  save_to_png(), so the ASCII/PyGame/browser views all agree visually.
  Show the colored solution grid for whatever's most recently found
  or in progress, plus running stats aggregated by the server -
  overall rate, ETA (see the progress-rate/ETA idea above), counts of
  unsearched/assigned/completed ranges, number of active clients, etc.

  Participation, not just spectating: the goal is for the browser
  client to actually help search, not just watch - compile the C++
  solver to WebAssembly (e.g. via emscripten) so a browser tab can
  request a range from the server, search it itself in a Web Worker
  (keeping the page responsive), and report progress/solutions back
  the same way a native client would. "Contribute a laptop's idle CPU
  to the search" with zero install beyond opening a page.
  Make this opt-in, controlled by UI in the page itself (e.g. a
  toggle/button - "Contribute my computer's spare cycles" - off by
  default so someone who just wants to watch isn't unexpectedly
  spinning up their CPU/fan/battery). While off, the page behaves as
  pure spectator, just rendering whatever the server reports; while
  on, it also requests and works ranges like any other client.
  This is more involved than the pure-spectator view (needs the WASM
  build of the solver working before it's useful), so it's fine for
  a first version to ship spectating only and add the participate
  toggle once that path is proven out - but the UI and protocol
  should be designed with this in mind from the start (e.g. the
  server shouldn't need to know or care whether a given client is
  native, a participating browser tab, or a spectating browser tab).

  Compiling to WASM: emscripten is the right tool - it lets rangesolver
  .cpp's already-optimized, already-verified backtracking logic be
  reused close to as-is, rather than risking a second implementation
  (in JS, or a WASM-native language like Rust/AssemblyScript) drifting
  out of sync with the native solver over time, and gets close to
  native speed for this kind of tight, array-heavy loop.
  - I/O needs to change: there's no real filesystem in the browser, so
    replace the current fopen/fprintf solution logging with exported
    JS callbacks instead (called on each solution found and each
    progress update) rather than trying to parse a virtual log file.
    This maps naturally onto what the client needs anyway - structured
    per-event data rather than text to parse.
  - Run each WASM instance inside a dedicated Web Worker so a long
    search doesn't freeze the page's UI thread.
  - For using multiple cores: prefer spinning up one independent
    single-threaded WASM worker per range request over a single
    multi-threaded WASM instance (pthreads), since the ranges are
    already embarrassingly parallel and this avoids needing
    SharedArrayBuffer's cross-origin-isolation deployment requirements.
